# BindHome product contract

This document describes the agreed functional behaviour that the user-facing
BindHome experience must implement.

It distinguishes current implementation from agreed target behaviour. A target
described here is not considered implemented until its backend support exists
and has been validated.

## Product principle

BindHome models the stable physical and functional identity of a home.

It is not a parallel Home Assistant platform.

Home Assistant remains authoritative for:

- Floors and Areas;
- Devices and Entities;
- entity state and availability;
- domains and entity platforms;
- supported features;
- services and service routing;
- integration-specific behaviour.

BindHome references Home Assistant objects where needed and owns only concepts
that Home Assistant does not already provide for this purpose.

## Core concepts

### Asset

An Asset is a stable physical element of the home.

Examples include:

- light points;
- sockets;
- switches;
- radiators;
- valves;
- taps;
- doors;
- windows;
- blinds;
- Ethernet outlets;
- antenna outlets;
- circuits;
- boilers;
- pumps;
- appliances;
- machinery.

An Asset may exist without automation, bindings, capabilities, relations or a
logical Home Assistant representation.

The minimum valid Asset remains:

- `name`;
- `asset_type`.

Its immutable internal ID is generated by BindHome.

### Area

`area_id` is a reference to a Home Assistant Area.

BindHome must not maintain a parallel Area or Floor catalogue.

Floor information is derived from Home Assistant through the referenced Area.

### Capability

A Capability describes a function of an Asset from BindHome's point of view.

Examples:

- `on_off`;
- `dimming`;
- `temperature`;
- `setpoint`;
- `power_measurement`;
- `open_close`;
- `position`.

Capabilities are extensible identifiers.

BindHome must not maintain a matrix describing which Home Assistant domains are
compatible with a capability.

### Binding

A Binding maps:

`Asset + Capability + Role -> Home Assistant entity_id`

The Home Assistant entity may be replaced without changing the Asset identity.

BindHome stores only the reference and its own binding metadata. Entity names,
devices, states, domains, Areas, manufacturers and supported features are read
from Home Assistant when needed rather than copied into BindHome.

### Relation

A Relation describes physical or functional topology between Assets.

Relations belong to BindHome because they model infrastructure relationships
that are not represented by Home Assistant's hardware registries.

Relation types remain extensible.

### Representation

Implemented as a first-class model.

A Representation describes whether and how BindHome exposes an Asset back into
Home Assistant as a logical entity.

Capability and Representation are different concepts.

Example:

- Asset: Living room ceiling light;
- capabilities: `on_off`, `dimming`;
- representation: `light`.

Another Asset may have `on_off` without being represented as a Home Assistant
Light.

An Asset currently supports zero or one primary Representation.

The persisted Representation stores the stable BindHome `asset_id` and the
BindHome-implemented logical platform.

Representation platforms are limited to logical platforms actually implemented
by BindHome. This does not attempt to catalogue every platform supported by Home
Assistant.

A Representation may define its own BindHome-side capability contract. The
current BindHome logical `light` implementation requires `on_off`. This
describes BindHome's implementation requirements, not Home Assistant domain
compatibility.

Creating an Asset with `on_off` does not automatically create a logical Light.
The Light appears only after an explicit `light` Representation is configured.

Removing a Representation removes the logical entity while preserving the
Asset. Re-adding it preserves the stable logical identity derived from the
Asset.

Registries written before Representation existed are migrated on load so Assets
that previously produced implicit logical lights keep that behaviour. Once
saved by the current model, the `representations` collection is explicit; an
empty collection means no logical exposure.

## Inventory-first workflow

This is the next user-facing milestone. Its required backend foundations are
implemented.

The primary user workflow is inventorying the home, not configuring automation.

A typical sequence is:

1. choose a Home Assistant Floor and Area;
2. describe how many common physical elements are present;
3. review the generated Asset draft;
4. create all Assets in one atomic operation;
5. enrich individual Assets later with better names, topology, bindings and
   logical representations.

A user must be able to document an entirely passive home before connecting any
smart hardware.

## High-volume creation

Creating Assets one by one is not the primary workflow.

BindHome must support high-volume inventory suitable for a normal home
containing hundreds of physical elements.

### Room inventory

The preferred workflow asks for quantities of common elements inside an Area.

Example:

- 3 light points;
- 9 sockets;
- 2 Ethernet outlets;
- 1 antenna outlet;
- 2 radiators;
- 3 windows;
- 3 blinds;
- 2 doors.

BindHome creates a draft such as:

- Light point 1;
- Light point 2;
- Light point 3;
- Socket 1;
- Socket 2;
- ...

The user may accept the generated names and improve them later.

### Quick add

A secondary workflow adds one Asset rapidly inside the currently selected Area.

### Bulk table

An advanced workflow permits spreadsheet-like editing or pasting of many Asset
rows before one save operation.

### Duplicate inventory

A completed room inventory may be duplicated to one or more other Areas.

Duplication copies the inventory structure only.

It must not copy:

- Asset IDs;
- bindings;
- Home Assistant entity references;
- logical entity identities.

Each copied Asset receives its own stable identity.

## Creation presets

BindHome provides convenient built-in presets for common home
infrastructure.

Examples include:

Electrical:

- light point;
- socket;
- switch;
- electrical panel;
- circuit;
- junction box.

Network and communications:

- Ethernet outlet;
- telephone outlet;
- antenna outlet;
- Wi-Fi access point.

Climate:

- radiator;
- thermostat;
- fan;
- air-conditioning unit.

Water:

- tap;
- shut-off valve;
- valve;
- drain;
- manifold.

Building:

- door;
- window;
- blind;
- skylight.

Equipment:

- boiler;
- water heater;
- pump;
- freezer;
- appliance;
- machine.

Presets are UX metadata, not backend restrictions.

The initial built-in catalogue contains 29 presets across six inventory groups:
electrical, network, climate, water, building and equipment.

A preset contains only:

- `preset_id`;
- inventory `group`;
- suggested `asset_type`;
- default display name;
- suggested capabilities.

The catalogue is exposed read-only through `bindhome/presets/list`.

The user may modify the suggested Asset draft values before saving.

Custom Asset types and custom capabilities remain supported.

A preset suggestion must never become a hidden compatibility rule. Presets do
not create bindings, Home Assistant entity references or logical
Representations, and there is deliberately no separate `create_from_preset`
write path. Drafts are saved through the ordinary Asset creation APIs,
especially transactional bulk creation for room inventory.

## Inventory before automation

Bulk inventory creation does not automatically create Home Assistant logical
entities.

For example, creating twelve physical sockets must not automatically create
twelve `switch` representations.

The lifecycle is intentionally separable:

`Inventory -> Connect -> Topology -> Expose/Automate`

This allows the physical model of the home to exist independently of its current
automation level.

## Transactional save semantics

High-volume creation must be atomic.

For a batch containing N Assets:

- all input is validated first;
- Home Assistant references such as Areas are validated against Home Assistant;
- all model and registry invariants are checked against a staged registry;
- persistence occurs once;
- staged state is adopted into the existing live registry only after successful
  persistence;
- the identity of the live registry object is preserved for long-lived runtime
  consumers;
- one registry-changed notification is emitted.

If any item is invalid, no Asset from the batch is committed.

The error response should identify the failing item clearly enough for the UX to
highlight the corresponding draft row.

Bulk creation must not be implemented as N independent client-side
`create_asset` calls.

## Preserving identity

Changing any of the following must preserve Asset identity:

- name;
- code;
- Area;
- capabilities;
- hardware binding.

Replacing physical smart hardware changes a Binding, not the Asset ID.

Enabling or disabling a logical Representation must not delete the Asset.

## Normal and advanced UX

Normal mode should use user-facing concepts:

- physical name;
- room;
- type;
- capabilities;
- connections;
- Home Assistant connection;
- status.

Internal identifiers such as Asset UUIDs, Binding IDs, raw entity IDs and
resolver details should be available in an advanced/debug view, not required for
normal household inventory.

## Status semantics

Configuration validity and runtime availability are distinct.

Examples:

- valid binding + entity available;
- valid binding + entity unavailable;
- valid binding + entity unknown;
- stale entity reference;
- missing binding;
- no logical Representation.

An offline device is not automatically a broken BindHome configuration.

## Editing and destructive operations

Forms use explicit Save / Cancel semantics.

Removing a capability that still has bindings must remain blocked until those
bindings are removed or reassigned.

Deleting an Asset must remain blocked while it is referenced by active BindHome
bindings, topology relations or a logical Representation.

Destructive operations must explain what blocks them rather than silently
cascading.

## Functional foundation status

The pre-UX functional foundation is complete:

1. P0-A: transactional bulk Asset creation -- implemented;
2. P0-B: explicit Representation model -- implemented;
3. P0-C: extensible creation presets -- implemented;
4. P0-D: architecture and product documentation synchronized with the
   implementation.

The first UX milestone is not a generic "Create Asset" form.

It is an Area-oriented **Inventory this room** workflow.

That UX should read Home Assistant Floors and Areas live, use the BindHome preset
catalogue to build editable local drafts, and persist the accepted room
inventory through `bindhome/assets/create_bulk`.
